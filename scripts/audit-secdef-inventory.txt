# Inventário SECURITY DEFINER — schema `public` (Live)

Data: 2026-05-09  
Total: **63** funções (15 trigger fns + 48 callables)

Todas têm `SET search_path = public` ✅.

Heurísticas usadas para classificar:
- `auth.uid()` — filtra pelo utilizador
- `has_role()` / `is_platform_admin()` — guard de role

- caller — onde é chamada (frontend grep / edge fn / cron / trigger / RLS / interno)

## Categoria D — Suspeitas / a investigar caso-a-caso (HIGH RISK)

Mutativas, **sem guard de role nem `auth.uid()` no body**. Confiam apenas em RLS, mas sendo `SECURITY DEFINER` o RLS é ignorado dentro do corpo. ⇒ qualquer `authenticated` pode invocar e modificar dados de outro tenant se conhecer um UUID.

**Patch D (template para cada função):**
```sql
CREATE OR REPLACE FUNCTION public.<fn>(...)
RETURNS ...
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp
AS $$
DECLARE
  v_event_company uuid;
BEGIN
  -- Guard 1: role
  IF NOT (public.has_role(auth.uid(),'admin'::app_role)
       OR public.has_role(auth.uid(),'manager'::app_role)
       OR public.is_platform_admin(auth.uid())) THEN
    RAISE EXCEPTION 'Forbidden' USING ERRCODE='42501';
  END IF;
  -- Guard 2: tenant (quando aplicável)
  SELECT company_id INTO v_event_company FROM public.events WHERE id = _event_id;
  IF v_event_company IS NULL OR v_event_company <> public.current_company_id() THEN
    RAISE EXCEPTION 'Cross-tenant operation denied' USING ERRCODE='42501';
  END IF;
  -- ... corpo original ...
END;
$$;
```

### Q3 — Snapshot de grants (baseline para rollback)
```sql
SELECT r.routine_name,
       string_agg(DISTINCT g.grantee, ',' ORDER BY g.grantee) AS grantees
FROM information_schema.routines r
LEFT JOIN information_schema.role_routine_grants g
  ON g.specific_name = r.specific_name AND g.privilege_type='EXECUTE'
WHERE r.specific_schema='public' AND r.security_type='DEFINER'
GROUP BY r.routine_name ORDER BY 1;
```
